# TrafficAI: Project Architecture & Workflow

This document serves as the complete technical blueprint for the TrafficAI Smart Management System. It outlines data structures, integrations, and the step-by-step lifecycle of the application.

---

## 1. Core Data Types and Structures

The system architecture utilizes several highly specific data types to rapidly pipeline visual information from the raw camera sensor to the final browser output.

*   **Video Feed (`cv2.VideoCapture`)**: Raw `.mp4` binary sequence parsed frame-by-frame.
*   **Frame (`numpy.ndarray`)**: A multi-dimensional array representing pixel data. It is dynamically reshaped to maintain its original aspect ratio while capped at a max width of `960px` for optimal processing speed.
*   **Model Weights (`best.pt`)**: The physical serialized PyTorch file representing the Custom-Trained AI brain.
*   **Bounding Boxes (`List[List[float]]`)**: The exact output array generated by the YOLO model in the format: `[x_min, y_min, x_max, y_max, confidence_score, class_id]`.
*   **Tracker Output (`List[Tuple]`)**: The array generated by the Euclidean tracker mapping temporal movement: `[x1, y1, x2, y2, Unique_Vehicle_ID]`.
*   **MJPEG Stream (`multipart/x-mixed-replace`)**: The byte-stream protocol used to push live video to the frontend. It operates by constantly firing boundary-separated `.jpg` images over HTTP.
*   **Stats API (`JSON Payload`)**: The RESTful packet consumed by the frontend every 1000ms:
    ```json
    {
      "zone_a_count": 8,
      "zone_b_count": 2,
      "total_unique": 142,
      "signal_a": "Green (30s)",
      "signal_b": "Red",
      "frame": 591,
      "status": "running"
    }
    ```

## 2. API Integrations: Roboflow Dataset

To construct a highly-accurate model, generic pre-trained weights (COCO) were discarded in favor of fine-tuning the model entirely on a traffic-specific dataset. 

### How Roboflow API Keys Were Utilized
The system utilized the *Roboflow SDK* within a Google Colab GPU-accelerated environment to securely pull the **"UA-DETRAC"** dataset. 
*   **API Execution**: `rf = Roboflow(api_key="SP9ZN2wKQIT39yHNZPOX")`
*   **Workspace & Project**: The code reached into the `brad-dwyer` cloud workspace and targeted the `ua-detrac` repository.
*   **Format Transformation**: The API seamlessly downloaded Version 1 of the dataset and automatically formatted all bounding-box annotations into the strict `.txt` format required explicitly by `yolov8`.

This process yielded gigabytes of specialized training images, allowing the YOLOv8 architecture to fine-tune its neural pathways to perfectly recognize vehicles from severe top-down overhead angles.

## 3. The Complete Application Workflow

This is the exact lifecycle of the system running in real-time.

### Step 1: Input Injection
1. The user opens the frontend Dashboard (`index.html`).
2. A video file (`.mp4`) is dragged and dropped onto the upload zone.
3. The JavaScript `XMLHttpRequest` fires a `multipart/form-data` payload containing the binary video to the Django backend `/upload/` endpoint.
4. Django streams the files into chunked blocks, saving it to `backend/data/` securely, bypassing RAM exhaustion.

### Step 2: The Assessment Loop (Generator)
1. Django immediately locks the video resource and starts the `generate_frames()` MJPEG loop.
2. OpenCV (`cv2`) grabs the first frame and calculates real-time aspect-ratio geometry to optimally scale the frame.
3. Every Nth frame (to save CPU cycles), the frame is passed into `yolo_detector.py`. 
4. The custom `best.pt` model scans the image array, instantly drawing bounding boxes around anything its neural network recognizes as a vehicle.

### Step 3: Tracking & Lane Slicing
1. The YOLO output boxes are injected into the mathematical `Euclidean Tracker`. The tracker compares the geometric distance of boxes from Frame 1 to Frame 2 to assign persistent `Unique IDs` across time.
2. The system splits the spatial frame strictly down the physical center (X-axis median). 
3. It iterates through every successfully tracked vehicle. If the center-point of the vehicle exists in `X < Center`, it increments **Lane A**. Otherwise, it increments **Lane B**.

### Step 4: Active Traffic Control Router
1. The aggregate snapshot of `(Lane A vs Lane B)` is passed to `decision.py`.
2. The logic engine acts as a physical Traffic Light. It compares the two sums. 
3. The heavily congested lane steals priority and gets assigned a Green Signal mapped dynamically to its congestion severity (15s, 30s, or 60s). The opposed lane is hardcoded to Red.

### Step 5: Visual Feedback & UI Render
1. The backend uses `cv2.addWeighted` to blend transparent blue and red visual lane dividers (Regions of Interest) directly onto the raw video pixels.
2. The bounding boxes, vehicle IDs, and UI stamps are drawn directly onto the image array.
3. The final composited frame is encoded into bytes and flushed out to the MJPEG stream.
4. Simultaneously, the frontend `script.js` fires a `fetch()` request every 1000ms to `/api/stats/`, digesting the JSON state and visually animating the dashboard's analytics cards and history sparklines.
